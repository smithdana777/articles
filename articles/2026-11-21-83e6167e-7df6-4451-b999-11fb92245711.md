# 支付表的 JSONB 字段查询与 GIN 索引

<!-- content-workspace-job:83e6167e-7df6-4451-b999-11fb92245711 -->

## 问题场景

支付表把扩展属性塞进 JSONB 字段，查询时用 ->> 取值再比较，数据一多就全表扫，接口从几十毫秒涨到几秒。

## 实现步骤

包含关系用 @> 判断，语义清晰且能命中 GIN 索引。

```sql
SELECT id FROM payments WHERE payload @> '{"paid_at": 1}';
```

建 GIN 索引，注意操作符类要选对，默认支持包含与存在判断。

```sql
CREATE INDEX idx_paid_at ON payments USING GIN (payload);
```

只取个别键时用 ->> 输出文本，需要类型转换就在表达式里显式转。

```sql
SELECT id, payload->>'paid_at' AS v
FROM payments WHERE payload ? 'paid_at' LIMIT 5;
```

## 注意事项

GIN 索引写入比 B-tree 慢，更新频繁的字段要评估；jsonb_path_ops 体积更小但只支持 @>，需要键存在判断时要用默认操作符类。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，减少不必要的返工成本。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

## 问题场景

货位导出要拉取多个分片再合并成一份文件，串行执行时总耗时随分片数线性增长。

## 实现步骤

按分片编号构造任务，提交到固定大小的线程池，池大小取分片数与 CPU 核数的折中。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def pull(part):
    rows = load_part("bin", part)
    return part, len(rows), rows
```

每个任务只负责自己那段数据并返回结果对象，主线程用 as_completed 按完成顺序收集。

```python
def export(parts, workers=6):
    out = {}
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futs = {pool.submit(pull, p): p for p in parts}
        for f in as_completed(futs):
            part, n, rows = f.result()
```

## 注意事项

线程池不适合 CPU 密集逻辑，GIL 会让加速比趋近于 1；任务里不要直接写同一个文件句柄，交回主线程统一写。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，让容量规划更有依据。

针对这类偶发问题，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

在跨团队协作时，要避免在高峰期执行这类操作，使整体改动风险可控。

从长期维护角度看，先把最小可复现的用例固定下来，让容量规划更有依据。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，并保留回滚开关以便快速恢复。

上线初期，要把异常路径和正常路径分别覆盖一遍，减少不必要的返工成本。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

在资源受限的环境下，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

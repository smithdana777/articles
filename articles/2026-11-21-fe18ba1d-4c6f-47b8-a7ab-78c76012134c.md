# 读懂日志表查询的 EXPLAIN ANALYZE 输出

<!-- content-workspace-job:fe18ba1d-4c6f-47b8-a7ab-78c76012134c -->

## 问题场景

日志表的接口慢，看执行计划觉得没问题，因为看的是预估。预估行数和实际差了两个数量级，优化器据此选错了连接方式。

## 实现步骤

加 ANALYZE 拿到真实执行数据，逐节点的 actual time 是排查重点。

```sql
EXPLAIN ANALYZE SELECT * FROM logs WHERE created_at > 1000;
```

加 BUFFERS 看缓存命中，大量读磁盘说明缓存不够或扫描过多。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM logs WHERE created_at > 1000;
```

对比预估与实际行数，差距大就更新统计信息或调大采样比例。

```sql
SELECT relname, seq_scan, idx_scan
FROM pg_stat_user_tables WHERE relname = 'logs';

// 预期：控制台输出与上文描述一致
```

## 注意事项

ANALYZE 会真实执行语句，写操作不要直接加；采样统计对倾斜数据不准，必要时对特定列调高统计目标。

上线初期，要把边界条件列成清单逐项确认，以便后续复盘有据可查。

从成本角度看，应当限定作用范围避免影响其他业务，保证每一步都可验证。

针对这类偶发问题，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

从排障效率看，要明确各项资源的释放时机，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

如果数据量继续增长，需要评估对现有调用方的影响面，减少不必要的返工成本。

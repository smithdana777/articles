# 用幂等键防止消息重复提交

<!-- content-workspace-job:e11c876e-3ddf-45a1-b63f-040c8dd50ebc -->

## 问题场景

消息的创建接口在超时重试时被调了两次，用户看到两条记录。前端加了防抖，但网络重试和网关重放照样能打进来。

## 实现步骤

客户端带一个请求 id，服务端用 setIfAbsent 抢占，抢不到直接返回重复。

```java
String key = "idem:" + req.getRequestId();
Boolean ok = redis.opsForValue()
    .setIfAbsent(key, "1", Duration.ofMinutes(10));
if (Boolean.FALSE.equals(ok)) {
    return Resp.duplicate();
}
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

数据库侧再加唯一约束，防止 Redis 失效时出现漏网。

```sql
INSERT INTO idempotent (req_id) VALUES (?);
```

处理成功后才写结果缓存，中途异常要释放占位，否则会卡住重试。

```java
System.out.println(redis.hasKey(key));
System.out.println(redis.getExpire(key));
```

## 注意事项

幂等键的有效期要覆盖重试窗口，太短起不到作用；占位与业务写入不在同一事务里，异常分支必须显式删除占位。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从排障效率看，应定期回顾相关监控指标，防止出现隐性回归。

从排障效率看，要明确各项资源的释放时机，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

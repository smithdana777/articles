# 给学员请求加上超时与取消能力

<!-- content-workspace-job:ab5ac753-af63-4ce5-8846-39fbfbb26b2d -->

## 问题场景

学员页面的接口偶尔长时间无响应，按钮一直转圈，用户重复点击又叠加出多个请求。

## 实现步骤

每次请求创建独立的 AbortController，并用定时器在超时后调用 abort。

```javascript
function timedFetch(url, ms = 8000) {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), ms);
  return fetch(url, { signal: ctrl.signal })
    .finally(() => clearTimeout(timer));
}
```

把 signal 传给 fetch，中止后进入 catch 分支并识别 AbortError。

```javascript
async function load(ident) {
  try {
    const res = await timedFetch(`/api/student/${ident}`, 3000);
    return await res.json();
  } catch (e) {
    return { error: e.name === 'AbortError' ? '超时' : '失败' };
  }
}
```

## 验证方法

把超时设为 1 秒访问一个慢接口，应在 1 秒左右抛出中止错误而不是无限等待。

## 注意事项

abort 之后 promise 以异常结束，必须捕获否则会出现未处理拒绝；同一个 controller 不能复用给多次请求。

对于刚接手的同学，应定期回顾相关监控指标，降低同类问题再次发生的概率。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。

在多人协作的项目里，应当限定作用范围避免影响其他业务，同时把结论沉淀进团队文档。

在实际落地时，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

对于刚接手的同学，应定期回顾相关监控指标，降低同类问题再次发生的概率。

从排障效率看，应定期回顾相关监控指标，防止出现隐性回归。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

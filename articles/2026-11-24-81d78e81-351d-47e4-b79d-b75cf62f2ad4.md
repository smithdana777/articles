## 问题场景

统计积分日志里的异常数量时，先把整个文件读成列表再层层过滤，单文件几百兆就吃满内存。

## 实现步骤

第一段逐行读并解析成字典，第二段过滤出目标级别，第三段做计数。

```python
def lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")
```

各段之间用 yield 传递，不构造中间列表，内存占用与文件大小无关。

```python
def parsed(rows):
    for r in rows:
        parts = r.split(" ")
        if len(parts) >= 3:
            yield {"level": parts[1], "msg": " ".join(parts[2:])}
```

每个生成器只做一件事，便于单独替换解析规则或过滤条件。

```python
def count(rows, level="ERROR"):
    return sum(1 for r in rows if r["level"] == level)

print(count(parsed(lines("point.log"))))
# 异常时先检查入参与依赖版本
```

## 注意事项

生成器只能遍历一次，重复统计要重新构造；异常处理放在最内层，否则一条坏行会中断整条管道。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

结合团队现状，可以通过压测确认容量水位，便于横向对比不同方案的效果。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

如果数据量继续增长，需要评估对现有调用方的影响面，减少不必要的返工成本。

从成本角度看，应当拆分步骤以便中途校验，避免资源被长期占用。

在实际落地时，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

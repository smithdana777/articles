# 为消息表的size统计建覆盖索引消除回表

<!-- content-workspace-job:c93099d7-d65f-4f40-beec-7197ef91206a -->

## 问题场景

消息表的汇总查询只用到size一列，却每次都回表几百万次，磁盘读放大严重，统计接口常年占着数据库三成负载。

## 实现步骤

确认查询涉及的列，全部放进联合索引，形成覆盖。

```sql
SELECT size, COUNT(*) FROM messages GROUP BY size;
```

索引列顺序按等值在前、范围在后排列，最左前缀才用得上。

```sql
CREATE INDEX idx_size ON messages (size, id);
```

用 EXPLAIN 的 Extra 列确认出现 Using index，说明没有回表。

```sql
EXPLAIN SELECT size FROM messages WHERE size > 1024;
```

## 注意事项

覆盖索引会让索引变大，写入成本上升，更新频繁的表要权衡；SELECT * 一定会回表，统计查询应显式列出需要的列。

从成本角度看，应当限定作用范围避免影响其他业务，同时把结论沉淀进团队文档。

上线初期，要把边界条件列成清单逐项确认，让排查路径更短。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，避免问题积累到难以收场。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

在压测阶段，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

遇到复杂链路时，优先保证失败时能快速定位原因，确认指标平稳后再逐步放开。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

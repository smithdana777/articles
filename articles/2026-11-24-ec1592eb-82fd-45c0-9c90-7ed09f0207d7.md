## 问题场景

统计访问令牌日志里的异常数量时，先把整个文件读成列表再层层过滤，单文件几百兆就吃满内存。

## 实现步骤

第一段逐行读并解析成字典，第二段过滤出目标级别，第三段做计数。

```python
def lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")
```

各段之间用 yield 传递，不构造中间列表，内存占用与文件大小无关。

```python
def parsed(rows):
    for r in rows:
        parts = r.split(" ")
        if len(parts) >= 3:
            yield {"level": parts[1], "msg": " ".join(parts[2:])}
```

每个生成器只做一件事，便于单独替换解析规则或过滤条件。

```python
def count(rows, level="ERROR"):
    return sum(1 for r in rows if r["level"] == level)

print(count(parsed(lines("token.log"))))
# 异常时先检查入参与依赖版本
```

## 注意事项

生成器只能遍历一次，重复统计要重新构造；异常处理放在最内层，否则一条坏行会中断整条管道。

从成本角度看，应当限定作用范围避免影响其他业务，保证每一步都可验证。

上线初期，要把边界条件列成清单逐项确认，让容量规划更有依据。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使运维成本保持在合理区间。

在实际落地时，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

从成本角度看，应当拆分步骤以便中途校验，让新人上手时少走弯路。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

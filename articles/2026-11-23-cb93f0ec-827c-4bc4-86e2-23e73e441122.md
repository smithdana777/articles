## 问题场景

每个用例都重新建一遍供应商表并插入初始数据，测试跑得慢，且初始化代码复制得到处都是。

## 实现步骤

用 session 级 fixture 建库建表，function 级 fixture 负责清理本次用例产生的行。

```python
import pytest, sqlite3

@pytest.fixture(scope="session")
def conn():
    c = sqlite3.connect(":memory:")
```

fixture 通过 yield 交出连接，测试结束后在同一位置执行回滚或删除。

```python
@pytest.fixture
def seeded(conn):
    conn.executemany("INSERT INTO suppliers (id, rating) VALUES (?, ?)",
                     [(i, i * 2.0) for i in range(1, 5 // 10 + 2)])
    yield conn
```

把常用查询封装成小工具函数，测试函数里只保留业务断言。

```python
def test_count(seeded):
    n = seeded.execute("SELECT COUNT(*) FROM suppliers").fetchone()[0]
    assert n == 5 // 10 + 1 and n > 0
```

## 验证方法

执行 pytest -q 观察用例数量与通过率，并用 --durations 确认初始化耗时已下降。

## 注意事项

session 级 fixture 里的连接不能跨用例残留未提交事务，否则后续用例会读到脏数据；yield 之后的清理代码即使断言失败也会执行。

在多人协作的项目里，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，减少不必要的返工成本。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，同时把结论沉淀进团队文档。

从排障效率看，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，让容量规划更有依据。

从成本角度看，应当拆分步骤以便中途校验，避免资源被长期占用。

从排障效率看，应定期回顾相关监控指标，降低同类问题再次发生的概率。

对稳定性要求高的场景，需要评估对现有调用方的影响面，减少不必要的返工成本。

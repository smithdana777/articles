## 问题场景

部门导出要拉取多个分片再合并成一份文件，串行执行时总耗时随分片数线性增长。

## 实现步骤

按分片编号构造任务，提交到固定大小的线程池，池大小取分片数与 CPU 核数的折中。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def pull(part):
    rows = load_part("dept", part)
    return part, len(rows), rows
```

每个任务只负责自己那段数据并返回结果对象，主线程用 as_completed 按完成顺序收集。

```python
def export(parts, workers=6):
    out = {}
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futs = {pool.submit(pull, p): p for p in parts}
        for f in as_completed(futs):
            part, n, rows = f.result()
```

## 注意事项

线程池不适合 CPU 密集逻辑，GIL 会让加速比趋近于 1；任务里不要直接写同一个文件句柄，交回主线程统一写。

如果数据量继续增长，需要评估对现有调用方的影响面，确保线上行为始终可控。

对于刚接手的同学，应定期回顾相关监控指标，降低同类问题再次发生的概率。

从排障效率看，应定期回顾相关监控指标，防止出现隐性回归。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

在多人协作的项目里，应当拆分步骤以便中途校验，避免资源被长期占用。

从可观测性角度，应确认依赖版本与运行环境一致，让容量规划更有依据。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，以便快速定位瓶颈。

在资源受限的环境下，建议在变更前留一份可回滚的快照，便于横向对比不同方案的效果。

针对这类偶发问题，尽量把决策依据写进变更说明，避免资源被长期占用。

从成本角度看，应当限定作用范围避免影响其他业务，保证每一步都可验证。

# 账务表单在提交前做集中校验并聚焦首个错误

<!-- content-workspace-job:e1cbcb3f-88a9-47ea-a6bb-0a8d9bc5df86 -->

## 问题场景

账务录入表单有十多个字段，校验分散在提交回调里，用户只看到顶部一个笼统提示。

## 实现步骤

用规则对象描述每个字段的必填、长度与格式要求。

```javascript
const rules = {
  name: (v) => (v.trim().length >= 2 ? '' : '名称至少 2 个字'),
  credit: (v) => (/^\d+$/.test(v) ? '' : '账务必须为数字'),
};
```

提交时遍历规则收集错误，把提示挂到对应字段下方。

```javascript
function validate(form) {
  const errors = {};
  for (const [k, fn] of Object.entries(rules)) {
    const msg = fn(form.elements[k].value);
    if (msg) errors[k] = msg;
  }
  return errors;
}
```

## 注意事项

异步校验要避免竞态，后发的请求可能先返回；聚焦前先确认元素仍然可见，隐藏字段无法获得焦点。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，以便后续复盘有据可查。

上线初期，要把边界条件列成清单逐项确认，让排查路径更短。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，避免问题积累到难以收场。

从长期维护角度看，优先保证失败时能快速定位原因，以便快速定位瓶颈。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，之后再考虑扩大适用范围。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使运维成本保持在合理区间。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从长期维护角度看，先把最小可复现的用例固定下来，以便后续复盘有据可查。

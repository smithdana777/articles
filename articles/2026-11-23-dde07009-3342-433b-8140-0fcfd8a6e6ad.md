## 问题场景

每个用例都重新建一遍相册表并插入初始数据，测试跑得慢，且初始化代码复制得到处都是。

## 实现步骤

用 session 级 fixture 建库建表，function 级 fixture 负责清理本次用例产生的行。

```python
import pytest, sqlite3

@pytest.fixture(scope="session")
def conn():
    c = sqlite3.connect(":memory:")
```

fixture 通过 yield 交出连接，测试结束后在同一位置执行回滚或删除。

```python
@pytest.fixture
def seeded(conn):
    conn.executemany("INSERT INTO albums (id, tracks) VALUES (?, ?)",
                     [(i, i * 2.0) for i in range(1, 12 // 10 + 2)])
    yield conn
```

```python
def test_count(seeded):
    n = seeded.execute("SELECT COUNT(*) FROM albums").fetchone()[0]
    assert n == 12 // 10 + 1 and n > 0
```

## 验证方法

执行 pytest -q 观察用例数量与通过率，并用 --durations 确认初始化耗时已下降。

## 注意事项

session 级 fixture 里的连接不能跨用例残留未提交事务，否则后续用例会读到脏数据；yield 之后的清理代码即使断言失败也会执行。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使运维成本保持在合理区间。

在跨团队协作时，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

在资源受限的环境下，要避免在高峰期执行这类操作，保证每一步都可验证。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

在跨团队协作时，建议在变更前留一份可回滚的快照，避免资源被长期占用。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

# 用 SSE 向发票页面推送实时状态

<!-- content-workspace-job:fc28189a-d515-4c16-8d0e-c04273b12e6e -->

## 问题场景

发票的进度页面用轮询，每秒一次，几百个用户同时打开就把接口打满，大部分请求还没有新数据。

## 实现步骤

服务端保持长连接，响应头声明事件流类型并关闭缓存。

```typescript
res.writeHead(200, {
  "Content-Type": "text/event-stream",
  "Cache-Control": "no-cache",
  Connection: "keep-alive",
});
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

有新数据就往连接里写一条事件，格式是 data 加空行。

```typescript
const timer = setInterval(() => {
  res.write(`data: ${JSON.stringify({ t: Date.now() })}\n\n`);
}, 1000);
```

客户端断开时清理定时器，否则连接关了还在往里写，服务端句柄泄漏。

```typescript
req.on("close", () => {
  clearInterval(timer);
  res.end();
});
```

## 注意事项

SSE 只支持服务端到客户端单向通信，需要双向就用 WebSocket；中间代理可能缓冲响应，要显式关闭缓冲并调大超时。

遇到复杂链路时，先把最小可复现的用例固定下来，让排查路径更短。

在跨团队协作时，要避免在高峰期执行这类操作，避免问题积累到难以收场。

上线初期，要把边界条件列成清单逐项确认，降低同类问题再次发生的概率。

在压测阶段，尽量把决策依据写进变更说明，便于横向对比不同方案的效果。

从排障效率看，要明确各项资源的释放时机，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

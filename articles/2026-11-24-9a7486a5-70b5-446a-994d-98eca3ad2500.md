## 问题场景

部门批处理整体跑了四分多钟，开发者凭感觉怀疑是数据库慢，改了半天没有效果。

## 实现步骤

用 cProfile 包住主流程跑一次，输出按累计时间排序的统计表。

```python
import cProfile, pstats

def profile(fn, out="prof.out"):
    cProfile.runctx("fn()", globals(), {"fn": fn}, out)
    return pstats.Stats(out)
# 重复执行结果幂等
# 异常时先检查入参与依赖版本
```

只看前十个函数，区分自身耗时与调用子函数带入的耗时。

```python
def report(path, top=10):
    st = pstats.Stats(path).sort_stats("cumulative")
    st.print_stats(top)
    return st.total_tt
```

针对热点做单点改动后重跑同一份剖析，用数字确认是否真的变快。

```python
total = report("prof.out", top=8)
print("total_seconds", round(total, 3))
```

## 注意事项

cProfile 会放大函数调用开销，对短小函数密集的代码结果偏悲观；线上环境用采样剖析更合适。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

对于刚接手的同学，应定期回顾相关监控指标，降低同类问题再次发生的概率。

从排障效率看，应定期回顾相关监控指标，防止出现隐性回归。

在资源受限的环境下，要避免在高峰期执行这类操作，同时把结论沉淀进团队文档。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

在实际落地时，应确认依赖版本与运行环境一致，防止出现隐性回归。

从排障效率看，应定期回顾相关监控指标，以便后续复盘有据可查。

## 问题场景

每个用例都重新建一遍课程表并插入初始数据，测试跑得慢，且初始化代码复制得到处都是。

## 实现步骤

用 session 级 fixture 建库建表，function 级 fixture 负责清理本次用例产生的行。

```python
import pytest, sqlite3

@pytest.fixture(scope="session")
def conn():
    c = sqlite3.connect(":memory:")
```

fixture 通过 yield 交出连接，测试结束后在同一位置执行回滚或删除。

```python
@pytest.fixture
def seeded(conn):
    conn.executemany("INSERT INTO courses (id, duration) VALUES (?, ?)",
                     [(i, i * 2.0) for i in range(1, 240 // 10 + 2)])
    yield conn
```

把常用查询封装成小工具函数，测试函数里只保留业务断言。

```python
def test_count(seeded):
    n = seeded.execute("SELECT COUNT(*) FROM courses").fetchone()[0]
    assert n == 240 // 10 + 1 and n > 0
```

## 验证方法

执行 pytest -q 观察用例数量与通过率，并用 --durations 确认初始化耗时已下降。

## 注意事项

session 级 fixture 里的连接不能跨用例残留未提交事务，否则后续用例会读到脏数据；yield 之后的清理代码即使断言失败也会执行。

如果数据量继续增长，需要评估对现有调用方的影响面，以便快速定位瓶颈。

对稳定性要求高的场景，需要评估对现有调用方的影响面，减少不必要的返工成本。

从排障效率看，应定期回顾相关监控指标，以便后续复盘有据可查。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

从长期维护角度看，先把最小可复现的用例固定下来，让容量规划更有依据。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，并保留回滚开关以便快速恢复。

在多人协作的项目里，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

在压测阶段，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。

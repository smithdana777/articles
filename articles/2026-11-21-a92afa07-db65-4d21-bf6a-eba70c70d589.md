# 工单表深分页查询改用延迟关联

<!-- content-workspace-job:a92afa07-db65-4d21-bf6a-eba70c70d589 -->

## 问题场景

工单表的后台列表翻到几千页时接口直接超时，LIMIT OFFSET 越往后越慢，因为前面那些行虽然不返回，却照样要被读取和丢弃。

## 实现步骤

先用覆盖索引把目标页的主键捞出来，这一步不回表，扫描量可控。

```sql
SELECT id FROM tickets WHERE priority > 90 ORDER BY id LIMIT 20 OFFSET 200000;
```

再拿这批主键回表取完整字段，回表次数等于页大小，与偏移量无关。

```sql
SELECT a.* FROM tickets a
JOIN (SELECT id FROM tickets WHERE priority > 90
      ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

对比两次执行计划，改造后应当只走索引扫描而不是全表扫。

```sql
EXPLAIN ANALYZE
SELECT a.* FROM tickets a
JOIN (SELECT id FROM tickets ORDER BY id LIMIT 20 OFFSET 200000) b
  ON a.id = b.id;
```

## 注意事项

延迟关联要求排序字段有序且能被索引覆盖，否则内层仍会 filesort；键集分页（记住上一页最后一个 id）比 OFFSET 更稳，但只支持顺序翻页。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

结合团队现状，可以通过日志补充上下文信息，使运维成本保持在合理区间。

遇到复杂链路时，先把最小可复现的用例固定下来，以便后续复盘有据可查。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确保线上行为始终可控。

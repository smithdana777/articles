## 问题场景

照片调用异常被统一捕获后重新抛出自定义异常，日志里只剩“操作失败”，原始堆栈丢失。

## 实现步骤

捕获底层异常后用 raise ... from e 重新抛出，保留 __cause__。

```python
class CallError(RuntimeError):
    def __init__(self, ident, cause):
        super().__init__("照片调用失败: %s" % ident)
        self.ident = ident
        self.cause_type = type(cause).__name__
```

自定义异常携带业务标识，日志同时打印 cause 的类型与消息。

```python
def call(ident):
    try:
        return do_request(ident)
    except (TimeoutError, ConnectionError) as e:
        raise CallError(ident, e) from e
```

## 注意事项

raise ... from None 会主动切断因果链，只有确定底层异常会误导时才用；异常包装不要丢失原错误码。

在迁移过程中，可以通过压测确认容量水位，避免资源被长期占用。

在跨团队协作时，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

遇到复杂链路时，优先保证失败时能快速定位原因，确保线上行为始终可控。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

在迁移过程中，可以通过压测确认容量水位，便于横向对比不同方案的效果。

从长期维护角度看，优先保证失败时能快速定位原因，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

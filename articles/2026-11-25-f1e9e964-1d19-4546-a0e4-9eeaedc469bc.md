## 问题场景

班次模块从字典读配置，键名拼错或类型不对时要等运行到深处才报错，排查成本很高。

## 实现步骤

用 dataclass 声明字段与默认值，在 __post_init__ 里做范围校验。

```python
from dataclasses import dataclass, field

@dataclass
class Config:
    name: str = "shift"
    limit: int = 8
    tags: list = field(default_factory=list)

    def __post_init__(self):
        if not 1 <= self.limit <= 100000:
            raise ValueError("limit 越界: %s" % self.limit)
```

从环境变量或文件读出原始字典后统一转换，非法值直接抛错并带上字段名。

```python
def parse(raw):
    return Config(name=raw.get("name", "shift"),
                  limit=int(raw.get("limit", 8)),
                  tags=list(raw.get("tags", [])))
```

c = parse({"limit": 8, "tags": ["hours"]})

## 验证方法

分别传入合法值与越界值，合法值应正常构造，越界值应抛出带字段名的异常。

## 注意事项

dataclass 默认不做类型检查，注释只是注释；可变默认值要用 field(default_factory=...)，直接写列表会共享同一个对象。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

结合团队现状，可以通过日志补充上下文信息，保证每一步都可验证。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

对稳定性要求高的场景，需要评估对现有调用方的影响面，减少不必要的返工成本。

如果数据量继续增长，需要评估对现有调用方的影响面，减少不必要的返工成本。

从成本角度看，应当拆分步骤以便中途校验，避免资源被长期占用。

在实际落地时，建议先在小流量环境验证行为是否符合预期，确认指标平稳后再逐步放开。

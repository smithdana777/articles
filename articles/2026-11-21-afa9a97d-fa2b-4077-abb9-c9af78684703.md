# 用 saga 编排运单的跨服务事务

<!-- content-workspace-job:afa9a97d-fa2b-4077-abb9-c9af78684703 -->

## 问题场景

运单下单要跨订单、库存、支付三个服务，用本地事务包不住。中间某一步失败后，前面已经扣掉的库存没人释放，数据就对不上了。

## 实现步骤

把流程拆成若干本地事务，每一步都实现对应的补偿操作。

```java
try {
    orderService.create(o);
    stockService.lock(o);
    payService.charge(o);
} catch (Exception e) {
    payService.refund(o);
    stockService.unlock(o);
    orderService.cancel(o);
}
// 该片段可重复执行，结果保持不变
```

失败时按逆序执行已成功步骤的补偿，注意补偿本身也可能失败。

```java
void compensate(Runnable step, String key) {
    if (done.add(key)) {
        step.run();
    }
}
```

补偿必须幂等，重复执行不能产生副作用，否则重试会越补越乱。

```java
System.out.println(done.size());
System.out.println(done.contains("refund"));
```

## 验证方法

人为让支付步骤失败，库存应被释放、订单应变为已取消，最终数据一致。

## 注意事项

saga 没有隔离性，中间状态对外可见，需要业务上容忍或用状态机控制；补偿失败要有兜底对账，不能只靠重试。

在压测阶段，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。

从可观测性角度，应确认依赖版本与运行环境一致，以便后续复盘有据可查。

在跨团队协作时，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

遇到复杂链路时，优先保证失败时能快速定位原因，确保线上行为始终可控。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

在迁移过程中，可以通过压测确认容量水位，便于横向对比不同方案的效果。

从长期维护角度看，优先保证失败时能快速定位原因，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。
